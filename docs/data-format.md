# 資料格式規格

桌面版（Python）與之後的手機版（Flutter／Dart）共用這份規格。兩邊的實作都要通過 `tests/golden/` 的標準測試資料。

## 1. 時間與識別

| 項目 | 格式 | 例子 |
|---|---|---|
| 日期 `date`／`start_date`／`end_date` | `YYYY-MM-DD`（使用者當地日期） | `2026-11-02` |
| 時間 `time`／`start_time`／`end_time` | `HH:MM`（使用者當地時間，24 小時制） | `14:05` |
| 時間戳記 `created_at`／`updated_at`／`deleted_at` | UTC，固定到毫秒，結尾 `Z` | `2026-11-02T06:05:00.123Z` |
| 紀錄 `uuid` | UUID v4 字串 | `33333333-3333-4333-8333-333333333333` |
| 分類 `uuid` | 新建時用 UUID v5 由完整路徑算出（見下方），之後改名或移動都不變 | |
| 裝置 `device_id` | UUID v4，每個資料庫建立時產生一次 | |

時間戳記格式固定，所以可以直接用字串比較大小。Dart 的 `toIso8601String()` 可能輸出微秒，必須自行格式化成三位毫秒。

分類的 uuid：`uuid5(7d4f2a3e-5b1c-4e8a-9f60-2c3d4e5f6a7b, 路徑名稱用 "\n" 串起來)`，例如「開發 › 專案A」是 `uuid5(ns, "開發\n專案A")`。兩台裝置各自建立（或從舊資料轉換出）相同路徑的分類時會得到同一個 uuid，同步時自然合併。如果算出來的 uuid 已經被別的分類用掉（例如某個分類改名後，又新增一個用舊名稱的分類），改用隨機的 UUID v4。

## 2. 狀態

| 值 | 顯示 | 算未完成（會被帶入） |
|---|---|---|
| `todo` | 待辦 | 是 |
| `doing` | 進行中 | 是 |
| `waiting` | 等待中 | 是 |
| `review` | 待確認 | 是 |
| `done` | 完成 | 否 |
| `cancelled` | 取消 | 否 |

舊版的 `blocked`（卡住）已改成 `todo`：資料庫升級（schema v5）時直接轉換，匯入資料包時也接受 `blocked` 並轉成 `todo`。舊版程式不認得新的狀態，所以要同步的裝置都需要更新到新版。

## 3. 資料包（bundle）

匯出、匯入、之後的區網同步都用同一種結構。可以是 zip 檔，也可以是資料夾：

```
bundle.json
images/2026-11-02/<檔名>.png
```

`bundle.json`：

```json
{
  "format": "reporttool-bundle",
  "version": 4,
  "device_id": "…",
  "exported_at": "2026-11-02T09:00:00.000Z",
  "categories": [
    {"uuid": "…", "parent": null, "name": "開發", "position": 0, "progress": 60, "priority": 1,
     "updated_at": "…", "deleted_at": null},
    {"uuid": "…", "parent": "<開發的 uuid>", "name": "專案A", "position": 0, "progress": null,
     "priority": 3, "updated_at": "…",
     "deleted_at": null}
  ],
  "entries": [
    {
      "uuid": "…",
      "date": "2026-11-02",
      "time": "10:20",
      "start_date": "2026-11-02",
      "start_time": "09:30",
      "end_date": "2026-11-02",
      "end_time": "10:20",
      "title": "登入頁 timeout",
      "text": "第一行\n第二行起是補充",
      "status": "doing",
      "priority": 3,
      "category": "<分類 uuid 或 null>",
      "tags": ["專案A"],
      "images": [{"path": "images/2026-11-02/<hex>.png", "original_name": "截圖", "include": true}],
      "carried_from": "<另一筆紀錄的 uuid 或 null>",
      "created_at": "…",
      "updated_at": "…",
      "deleted_at": null
    }
  ]
}
```

欄位說明：

- `time`：建立這筆紀錄的時間，只用來排序，介面上不顯示。
- `start_date` + `start_time`、`end_date` + `end_time`：這件事的起訖（時段），每筆紀錄都一定有（tombstone 也有）。
  - （`start_date`, `start_time`）不晚於（`end_date`, `end_time`）；相等表示時長 0。時長是實際經過的時間，可以跨午夜、跨好幾天。
  - 時段的日期可以和紀錄的 `date` 不同（例如補記、或帶入時沿用前幾天的時段）。使用者沒填日期就是 `date`。
  - 以 15 分鐘為一格（`:00`／`:15`／`:30`／`:45`）。存檔、匯入、資料庫升級（schema v9）時都四捨五入到最近一格（`09:07`→`09:00`、`17:08`→`17:15`），會進位到 `24:00` 的改成 `23:45`。匯入資料包時不整齊的時間不算錯，直接取整。
  - 新增紀錄時使用者沒填，就自動補：`end_time` ＝ `time` 取整，`start_time` ＝「前一則」的結束時間，沒有前一則就和 `end_time` 相同。
    「前一則」＝同一天（`date` 和 `end_date` 都是這天）、沒被刪除的紀錄中，不晚於（取整後的）`end_time` 的最晚 `end_time`。`time` 本身不取整。起訖日期都是 `date`。
  - 「帶入未完成項目」產生的紀錄沿用原本那筆的時段（含日期）。「追加進度」產生的紀錄起訖都是當下的時間取整（時長 0）。
- `title`：標題，可以是空字串。舊版匯出的資料包沒有這個欄位，匯入時當作空字串。`title` 和 `text` 至少要有一個不是空的（tombstone 除外）。
- `priority`：執行優先順序，整數 1~5，1 最優先，預設 3。舊版資料包沒有這個欄位，匯入時當作 3。
- `categories`：樹狀的分類（第一層叫分類，底下各層叫子分類，層數不限）。
  - `parent`：上一層的 uuid，`null` 表示第一層。
  - `position`：同一層之間的順序（使用者手動排序）。
  - `priority`：優先度 1~5（1 最優先），沒有這個欄位時當成 3。同一層先依 `priority`、再依 `position` 排列。
  - `progress`：使用者手動填的進度，整數 0~100，`null` 表示沒有設定。每個節點各自獨立，不會由子分類彙總。
  - 同一層的名稱不重複；名稱不能包含 `›`。完整路徑用 ` › ` 串起來，例如 `開發 › 專案A`。
- `category`：紀錄所屬的分類 uuid（任何一層都可以），`null` 表示未分類。一筆紀錄只屬於一個分類。
- `tags`：依使用者輸入的順序排列，不含 `#`。tag 只是標籤，不影響分組或排序。
- `images`：依顯示順序排列。
  - `path` 必須符合 `images/YYYY-MM-DD/[A-Za-z0-9_-]+.副檔名`，檔名用隨機 hex，所以跨裝置不會撞名。
  - `include: false` 表示「不給 AI」：回報時不輸出這張圖，只標示「附圖N：未提供」。
- `carried_from`：這筆紀錄是從哪一筆延續過來的（帶入未完成項目或追加進度），用來串起同一件工作的歷程。
- `deleted_at`：不是 `null` 時，這筆是 **tombstone**（已刪除的紀錄）。這時 `title`、`text` 是空字串，`category` 是 `null`，`tags` 和 `images` 都是空陣列。
- 程式自動建立的預設分類（開發、會議、支援、行政、其他）`updated_at` 是 `1970-01-01T00:00:00.000Z`，所以全新的資料庫匯入備份時，備份裡的排序與進度一定優先。
- 分類也有 tombstone。改名、移動只改分類本身，紀錄不用變。刪除分類時，底下的子分類一起變成 tombstone，裡面的紀錄移到被刪分類的上一層（第一層就變成未分類）。

### 舊版資料包（version 1、2、3）

第 1~3 版的紀錄沒有 `start_date`、`end_date`，匯入時都設成紀錄的 `date`（和資料庫升級 schema v10 相同，不更新 `updated_at`）。3.0 的程式只接受第 1~3 版，讀到第 4 版會整份拒絕。

第 1、2 版的紀錄也沒有 `start_time`、`end_time`，匯入時和資料庫升級（schema v8）用相同規則回推，不更新 `updated_at`：

1. 本機已經有同一筆、而且 `date`、`time` 都沒變時，沿用本機的起訖。
2. 其他的先設成 `end_time` ＝ `start_time` ＝ `time`；全部紀錄合併完後，`start_time` 改成「前一則」的結束時間（規則同上，不含自己；tombstone 不算）。結束時間都已經是 `time`，所以處理順序不影響結果。

回推出來的時長只是估計。2.x 的程式只接受第 1、2 版，讀到第 3 版會整份拒絕，不會默默丟掉起訖時間。

### 第 1 版的分類

第 1 版的分類只有一層、以名稱辨識（`categories` 只有 `name`、`position`、`updated_at`、`deleted_at`），紀錄的 `category` 是分類名稱。匯入時：

1. 分類對應到同名的第一層分類，新建時 uuid 用 `uuid5(ns, 名稱)`。
2. 紀錄合併完後，做和資料庫升級相同的轉換：紀錄的第一個 tag 變成它所屬分類底下的子分類（沒有分類就變成第一層），tag 本身保留，不更新 `updated_at`。

匯入前要先整份檢查格式，任何一項不合就整份不匯入。

## 4. 合併規則

把另一台裝置的 bundle 合併進本機：

1. 先合併分類（上層先、子分類後），再合併紀錄，最後接上 `carried_from`。
2. 紀錄和分類都用 `uuid` 對應本機資料。本機沒有的就新增，tombstone 也要新增，這樣之後不會被舊資料救回來。
   分類找不到相同 uuid、但同一層有同名的分類時，當作同一個分類。
3. 兩邊都有時，比較 `updated_at`，較新的勝出。完全相同時：
   1. 刪除優先；
   2. 都沒刪或都刪了：把兩邊的紀錄都轉成 JSON（key 排序、不跳脫中文），字串比較大的勝出。

   這樣兩台裝置不論合併順序如何，都會得到相同結果。
4. 紀錄勝出時，tag 和圖片清單整個以勝出的版本為準。本機多出來的圖片檔要刪除。本機沒有的圖片從 bundle 複製過來；bundle 裡也沒有檔案時，照樣記錄，回報會標示「檔案遺失」。
5. 分類比較時，整個分類（`parent`、`name`、`position`、`priority`、`progress`）以較新的版本為準。新的 `parent` 會造成循環時，保留本機的上層。
6. 紀錄用到的分類已經被刪除時，往上找第一個還在的分類；都刪了就是未分類。
7. 對方刪除分類時，本機的這個分類和子分類一起刪除，裡面的紀錄移到還在的上層，但**不更新**這些紀錄的 `updated_at`，以免蓋掉對方較新的版本。
8. 使用者在本機改 tag 名稱、刪除 tag、刪除分類時，受影響的紀錄都要更新 `updated_at`。分類改名、移動、改進度只更新分類的 `updated_at`。

## 5. 回報（report.md）

產生某一天的回報：

1. 取當天（`date`）沒被刪除的紀錄，依 `start_date`、`start_time` 排序，相同時再依 `time`、`created_at`。
2. 圖片依紀錄順序從 1 開始編號，**包含**沒勾「給 AI」的圖。
3. 輸出的圖檔名稱：`{編號兩位數}_{描述}{副檔名}`。
   - 描述取 `title`（空的話用 `text`）去掉頭尾空白後的第一行，移除所有空白、控制字元與 `\/:*?"<>|`，再去掉頭尾的 `.` 和空格，取前 20 個字；結果是空的就用 `image`。
   - 副檔名：原圖是 `.jpg`／`.jpeg` 時輸出 `.jpg`，其他一律 `.png`。
   - 長邊超過設定值（預設 1600）時等比例縮小，不放大。
4. 每筆紀錄一行（多行內容從第二行起縮排兩格）：

```
- [HH:MM–HH:MM Nh][狀態][優先N][分類：X][#tag1 #tag2] 內容（延續自 MM-DD）（![附圖1]、附圖2：未提供）
```

   - 開頭是時段與時數：`[09:00–10:30 1.5h]`。時數是分鐘數除以 60，最多兩位小數、去掉尾端的 0（50 分 → `0.83h`，60 分 → `1h`）；時段中間是 en dash `–`（U+2013）。時長 0 時只寫一個時間：`[16:40]`。
     時段不在紀錄那天時加上日期（`MM-DD`，和 `date` 不同年時寫完整日期）：同一天 `[10-30 09:00–10:30 1.5h]`，跨日 `[10-30 22:00–10-31 02:00 4h]`，時長 0 `[10-30 09:00]`。
   - 有標題時，內容前面加上 `【標題】`，例如 `- [09:00–09:30 0.5h][完成][優先3] 【週會】週會報告進度`。
   - `[優先N]` 每筆都會輸出；回報仍依起始時間排序，不依優先順序。
   - `[分類：X]` 的 X 是完整路徑，例如 `[分類：開發 › 專案A]`。沒有分類就省略 `[分類：X]`，沒有 tag 就省略 tag 那一段。
   - 「延續自」的日期是沿著 `carried_from` 一路往前找到的**最早**那筆紀錄的日期。
   - 有 `carried_from` 且那筆紀錄沒被刪除時，在這筆紀錄後面加上和**前一筆**（`carried_from` 指向的那筆）的比較：

     ```
       ⇄ 與 MM-DD 相比：狀態 待辦→進行中；優先 3→1；標題 A→B；分類 A→B；tag +#x -#y；內容有更新；新增附圖 N 張
         前：被刪掉或改掉的那一行
         後：新增或改過的那一行
     ```

     - 只列出有變的項目，依上面的順序，用「；」分隔；全部沒變就寫 `沒有變更`。空標題寫 `（無）`，未分類寫 `（未分類）`。
     - 前一筆和這筆同一天時，日期後面加上前一筆的起始時間：`與 MM-DD HH:MM 相比`。
     - 內容比較前先去掉頭尾空白與空白行，以行為單位（Python `difflib.SequenceMatcher`），相同的行不列出；每段改動先列「前」再列「後」。
     - 附圖張數是這筆紀錄的所有圖片（帶入時不會複製圖片）。
   - 圖片標示：沒勾「給 AI」→`附圖N：未提供`；檔案不存在→`附圖N：檔案遺失`；其他→Markdown 引用圖片 `![附圖N]`，檔名寫在檔案最後的引用定義。
   - PPT 的備忘稿不用引用寫法，有圖時寫成 `附圖N：檔名`。

5. 整份檔案：

```
# 工作回報整理請求（YYYY-MM-DD）

## 指示
{config/instructions.md 的內容，去掉頭尾空白}

## 今日工作紀錄
{每筆紀錄一行；沒有紀錄時寫「（今天沒有紀錄）」}

## 分類資訊
- 開發：優先1、進度 60%
- 開發 › 專案A
- 會議

[附圖1]: <01_xxx.png>
[附圖3]: <03_xxx.jpg>
```

   - 「## 分類資訊」：這份回報的紀錄用到的分類**以及它們的上層**，依分類樹的順序（先父後子，同層先依 `priority`、再依 `position`），格式 `- {完整路徑}`，有設定時後面加「：」與附註，用「、」分隔：優先度不是 3 時寫 `優先N`，有進度時寫 `進度 N%`。和紀錄之間空一行；沒有任何紀錄有分類時整段省略。
   - 最後一段是有輸出的圖片的引用定義，依編號排列，格式 `[附圖N]: <檔名>`（檔名用角括號包起來，含括號等符號也不會出錯）。和前一段之間空一行；沒有任何圖片輸出時整段省略。

完整的例子見 `tests/golden/basic/`：`bundle.json` 是輸入，`expected_report.md` 是用 `tests/golden/instructions.md` 當指示時應該產生的結果。

### 範圍整理

整理 `開始`～`結束`（含頭尾）的紀錄，輸出到 `report_{開始}_to_{結束}/`。同一件工作（同一條延續鏈）只列一次：

1. **分成工作**：沿著 `carried_from` 往上找到最上面那筆，相同的就是同一件工作。中間的紀錄被刪除或在範圍外也照樣串起來；一筆被延續成好幾筆（分岔）時，整棵樹還是同一件工作。
2. **排列**：工作依它在範圍內最早那筆的 `date`、`start_date`、`start_time`、`time`、紀錄 id 排列；工作內的紀錄也依同樣順序。圖片依這個輸出順序從 1 編號，整段期間連續。
3. **只有一筆的工作**：和單日的紀錄行相同，最前面多一個日期 `[MM-DD（X）]`：

   ```
   - [11-02（一）][09:30–10:00 0.5h][完成][優先3] 【週會】週會
   ```

4. **好幾筆的工作**：先一行工作摘要，底下縮排兩格列出每一筆：

   ```
   - 【工作名稱】[最新：完成、進行中][優先N][分類：X][#tag]（延續自 MM-DD）（範圍內 3 筆，合計 5h）
     - [11-02（一）][09:00–11:00 2h][進行中] 內容
       第二行起再縮排兩格
       ⇄ 與 10-30 相比：內容有更新
     - [11-03（二）][15:00–16:00 1h][進行中] 【分支的標題】內容（![附圖2]）
   ```

   - 「最新」：範圍內沒有被其他範圍內紀錄延續的那幾筆（也就是各分岔最新的一筆）的狀態，依時間排列、相同的只寫一次。
   - `[優先N][分類：X][#tag]` 用範圍內**最新**那筆的；沒有分類或 tag 時省略那一段。
   - 工作名稱：最新那筆的標題，沒有標題就用它的內容第一行；有分岔時改用範圍內**最早**那筆的。
   - 「延續自」：範圍內最早那筆沿著 `carried_from` 找到的最早日期，規則同單日。
   - 合計：範圍內各筆時長加總，寫法同時段的時數；起訖（含日期）完全相同的紀錄只算一次（帶入未完成項目會沿用時段）。總和是 0 時省略「，合計 …」。
   - 每一筆只寫日期、時段、狀態；標題和工作名稱不同時才寫 `【標題】`。和前一筆的比較只寫 `⇄ 與 … 相比：…` 那一行（前後內容已經都列出來，不再列「前：」「後：」）。

```
# 工作回報整理請求（{開始} ~ {結束}）

## 指示
{config/instructions.md 的內容，去掉頭尾空白}

## 期間工作紀錄（共 W 件工作、N 筆紀錄，D 天）
- …
```

沒有紀錄時，「## 期間工作紀錄（共 0 件工作、0 筆紀錄，0 天）」下面寫「（這段期間沒有紀錄）」。

期間工作紀錄後面接「## 工時統計」（和前一段之間空一行）：

```
## 工時統計
（每個分類都包含子分類；時段重疊的紀錄各自計算，沒有扣除重疊）
- 開發：3h（55%）
- 開發 › 專案A：2h（36%）
- 會議：2h（36%）
- 未分類：0.5h（9%）
- 合計：5.5h
```

- 每個分類的時數是這段期間它和所有子分類的紀錄時長加總，依分類樹的順序（同「## 分類資訊」）；時數是 0 的分類不列。每筆紀錄的時數算在它自己的分類（延續鏈中途改了分類也一樣）。同一件工作（同一條延續鏈）起訖完全相同的紀錄只算一次，算在範圍內最後那筆（它的分類）。
- 百分比是占「合計」的比例，四捨五入到整數；不是 0 但四捨五入成 0 時寫 `<1%`。因為上層包含子分類，各行加起來會超過 100%。
- 有未分類紀錄的時數時加「未分類」那一行；最後一行是全部的合計。
- 所有紀錄的時長都是 0 時，整段省略。

「## 分類資訊」與圖片引用定義接在後面，規則同上（以這段期間的所有紀錄為準）。

## 6. 標準測試資料（golden）

`tests/golden/<案例>/` 每個案例要通過兩項檢查：

1. 匯入 `bundle.json` 後產生 2026-11-02 的回報，內容必須和 `expected_report.md` **逐字相同**。

修改回報格式時，要同時更新 `expected_report.md` 與這份文件。
